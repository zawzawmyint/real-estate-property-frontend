# Development

For coding-agent runtime inspection, use the configured Next.js DevTools MCP connector and the [agent tooling workflow](agent-tooling.md). It preserves Webpack and supplements the quality gates below.

Use Node 24 LTS and Bun 1.3.14. Install via `bun install --frozen-lockfile`; commit lockfile changes when intentionally updating dependencies. `bun run` executes tools using Node unless a tool explicitly chooses another runtime.

Copy `.env.example` to `.env.local`. `API_URL` must be an HTTP(S) origin without path, query, credentials or fragment. Default: `http://localhost:4311`. Local files and credentials are ignored. Restart dev after configuration changes; rebuild production when changing the rewrite origin.

Public inquiry relay requires `INQUIRY_RELAY_SECRET` to exactly match the backend server-only value and be at least 32 characters. `INQUIRY_TRUSTED_CLIENT_HEADER` identifies the ingress-provided client header: trusted ingress must overwrite it, and direct access to Next must be blocked. Local loopback uses the development fallback. These settings are deployment configuration, never browser-exposed values.

For optional one-click local demo staff access, set `DEMO_STAFF_PASSWORD` in ignored `.env.local` to a 12–128-character value shared by the separately pre-provisioned local demo accounts, then restart `bun run dev`. Leave it empty or remove it to hide the Demo access controls. The frontend does not create those accounts. This setting works only when `NODE_ENV=development`; it is deliberately absent from production and test rendering. The configured value is supplied to the local browser for native sign-in, so use a local-only password that is never reused for real staff access.

Run the backend separately on port 4311, migrate its SQLite database and bootstrap an Admin, then `bun run dev` here on port 3100. `/crm` requires backend availability because it validates an Express session; public property routes request the backend and show a retry state when it is unavailable. Use matching development configuration locally. Production requires coordinated `NODE_ENV=production`, HTTPS frontend/backend origins and production cookie configuration; it has not been browser-tested in a deployment.

Before a feature, create `specs/<feature-name>/spec.md`. Define UI states, accessibility, API contract and acceptance. Coordinate contract changes with the backend rather than duplicating business types by hand. Verify acceptance and reconcile documentation before marking delivered.

Run `bun run check` for API drift, lint, formatting, typecheck, unit tests and production build. CI runs lint, formatting, typecheck, unit tests and build on Linux with no backend required; run `bun run api:check` locally as part of the complete gate. Unit tests cover the property action boundary, API transport, form safeguards, hydration and error handling.

Browser integration requires the isolated backend fixture, rather than a manually bootstrapped database. Install Chromium once using `bunx playwright install chromium`. In one PowerShell terminal at `backend/`, run `bun run db:generate`, then set a temporary 12–128 character `STAFF_E2E_PASSWORD` with `Read-Host -MaskInput` and start `bun run test:auth:e2e-server`. It provisions disposable SQLite accounts and property data, including dedicated desktop/mobile navigation Manager accounts, then cleans them up on Ctrl+C. In a second terminal at `frontend/`, set the same temporary `STAFF_E2E_PASSWORD` and run `bun run test:e2e`. Playwright starts its test-only proxy on 4312 for the disposable backend on 4311 and starts the Webpack frontend on 3100 with `API_URL=http://127.0.0.1:4312`. Its global setup warms routes before four parallel desktop/mobile workers run and saves screenshots in `test-results/`. Set `E2E_REUSE_FRONTEND=1` only when reusing a frontend already started with the same proxy configuration. Do not use a production password or database, and never ship the fixture/proxy as application behavior.

The disposable backend seeds fictional featured listings by default so public image tests are independent of other test files. Set `STAFF_E2E_SEED_PROPERTIES=0` only for targeted suites that do not need public listing media. Playwright automatically sets `E2E_TEST_RUN=1` on its Next server to hide the floating development indicator, which otherwise overlaps CRM account controls; compile/runtime errors remain enabled. Normal development and production do not require this flag. The long sign-in/refresh/sign-out/back-navigation journeys have a 60-second total budget while individual assertions retain their existing limits.

## Public agency catalog and portraits

The public Contact/Agents content is backend-authored in `backend/src/modules/agency/agency.catalog.ts`; it has no live CMS or Better Auth/staff-account synchronization. Update only approved public fields and `published` flags there. Direct contact values remain absent until approved, and the current catalog is fictional demo content, so Contact, directory and profile pages remain noindex.

Keep each catalog portrait path synchronized with a local file in [`public/images/agents/`](../public/images/agents/). Assets must be 800×1000 WebP files, and their provenance belongs in that directory's `README.md`. Deploy the frontend assets with the backend catalog change so a published path is never missing. Real-business publication requires approved direct contact details, profile/portrait approval and inquiry usage wording, plus review of the demo/indexing flags. See the [public contact and agent specification](../specs/public-contact-and-agents/spec.md) and its [backend-owned contract snapshot](contracts/public-contact-and-agents.md).

Public and CRM shells should remain usable at narrow widths, with keyboard navigation and visible focus. Review screenshots after layout changes. Avoid speculative UI tests that only assert static source wording.
